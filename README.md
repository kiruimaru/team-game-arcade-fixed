## Игровые механики

Наше общее состояние: `hp = 100`, `resources = 50`, `score = 0`, `turn = 1`.
Все действия подключены через `switch (choice)`.

1. **Рейд kiruimaru.** `rand() % 100` дает 50% успеха: игрок получает
   200–500 очков и столько же крышек. Поражение наносит 30–50 HP.
   Отсутствие крышек не запрещает рейд: иначе после проигрыша можно
   было бы заблокировать прохождение.
2. **Лагерь reyvii.** Перевязка стоит 10 крышек и дает до 10 HP;
   стимулятор стоит 25 и дает до 30 HP. Здоровье ограничено 100.
   Средства списываются только при доступной покупке; показывается
   фактически восстановленное здоровье.
3. **Казино Blypik.** Ставка равна `resources / 5`, то есть 20% с
   округлением вниз. При 0–4 крышках участие недоступно.
   Значения 0–49 дают выплату двух ставок и 100 очков;
   при 0 вместо 100 начисляется джекпот 500 очков.
   Значения 50–99 означают проигрыш ставки; при 99 дополнительно
   наносится 30 HP урона.

За выполненное действие начисляются еще 10 очков выживания, только если
герой жив. Отмена, неверная команда, отказ покупки и отказ ставки
не увеличивают счет и номер хода. Выход через `0` сохраняет счет.
Отрицательное здоровье ограничено нулем; накопление очков и крышек
ограничено `INT_MAX`, чтобы не допускать знакового переполнения.

| Модуль | Обнаруженная проблема | Подготовленное исправление |

| Лечение | Сообщалось номинальное, а не фактическое лечение | Выводим `min(heal, 100 - hp)` |
| Рулетка | `actionCompleted` не объявлена, `surrendered` вне области видимости | Используем исправленный общий цикл |
| Рулетка | `resources * 20` могло переполняться | Рассчитываем ставку через `/ 5` |

| Общий цикл | Неверный ввод прерывал обработку потока | Разбираем отдельную строку; EOF завершает игру |

Это технический аудит исходных веток, а не состоявшаяся переписка
Request changes / Approve в новом репозитории.

## Сборка и проверки

После слияния всех трех PR:

```bash
git switch main
git pull --ff-only
g++ game.cpp -o game
./game
```

Сохранили совместимость с исходным именем: `g++ main.cpp -o main`.
Компилировать `game.cpp` и `main.cpp` нужно по отдельности, не вместе:
`main.cpp` является совместимой точкой входа и включает `game.cpp`.

Строгая сборка и базовые проверки:

```bash
make test
```

Все проверки механик после объединения:

```bash
for module in risk heal gamble; do
  g++ -std=c++17 -Wall -Wextra -Wpedantic -Werror \
    -fsanitize=undefined -fno-sanitize-recover=all \
    "tests/${module}_tests.cpp" -o "build/${module}-tests" || exit 1
  "./build/${module}-tests" || exit 1
done
```

Сначала выполнить `make test`, чтобы создать `build/`.
В отдельной feature-ветке присутствует тест только ее механики.
GitHub Actions запускает базовую сборку и отдельную проверку механики.

В локально объединенной версии получены результаты:

```text
All game checks passed.
Risk checks passed (1000 seeds).
Healing checks passed (15 scenarios).
Gamble checks passed (1000 seeds and boundary cases).
```

Проверены смерть без бонуса хода, отсутствие средств, предел HP,
отмена покупки, неверный ввод, EOF, джекпот, проклятие и границы int.
При пробной партии выполнены рейд, лечение и рулетка; итог: **130 очков**.
Это технический smoke-test, не совместный турнир и не скриншот рекорда.

## Порядок завершения работы

1. Принимаем приглашения; назначаем задачи и рецензентов.
2. Каждый открывает свой PR в `main` с `Closes #1`, `#2` или `#3`.
3. Проверяем по кольцу: reyvii -> PR риска, Blypik -> PR лечения,
   kiruimaru -> PR рулетки. Скачиваем ветку и запускаем проверки.
4. Настоящий найденный дефект описываем у строки кода и отправляем
   Request changes. Не создаем искусственных багов или фиктивных замечаний.
5. Автор исправляет проблему `fix(...)`-коммитом в той же ветке;
   рецензент проверяет исправление, закрывает обсуждение и ставит Approve.
6. Сливаем через Squash and merge: риск, лечение, рулетка.
   Если после обновления ветки одобрение сброшено, получаем новое.
7. Удаляем ветки задач, проверяем автоматическое закрытие всех трех Issues.
8. Получаем `main`, запускаем игру и проводим совместную партию.
9. Прикладываем скриншоты защиты, трех историй review и итогового счета;
   обновляем таблицу фактического выполнения выше.

## Ответы на контрольные вопросы

**1. Чем GitHub Flow отличается от прямого push в main?**
Мы изолируем изменение в ветке, обсуждаем и проверяем его через PR,
а затем сливаем в стабильную `main`. Прямой push исключает этот
обязательный этап проверки.

**2. Почему Request changes блокирует слияние и как обновляется PR?**
При применимых правилах обязательного review запрос исправлений
препятствует слиянию до его разрешения. Автор отправляет новые коммиты
в ту же head-ветку, поэтому существующий PR обновляется автоматически.
Рецензент повторяет проверку и меняет решение на Approve.

**3. Что делает Closes #4?**
При слиянии PR в default-ветку GitHub автоматически закрывает
связанную задачу #4. Само открытие PR задачу не закрывает.

**4. Зачем Squash and merge?**
Все рабочие коммиты одного PR объединяются в один итоговый коммит.
В `main` остается компактная история завершенных задач, без отдельных
черновых шагов их реализации.

**5. Зачем Dismiss stale pull request approvals?**
Одобрение относится к проверенной версии кода. После новых коммитов
GitHub сбрасывает устаревшее одобрение: новую версию нужно проверить
заново, чтобы непроверенные изменения не прошли под старым Approve.
