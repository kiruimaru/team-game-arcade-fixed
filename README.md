## 3. Архитектура и игровые механики

Общее начальное состояние: `hp = 100`, `resources = 50`, `score = 0`,
`turn = 1`. В главном цикле действия выбираются через `switch (choice)`.
Случайные исходы определяются с помощью `rand() % 100`.

| Команда | Механика | Правила |
|---|---|---|
| `1` | Рейд в Пустошь | Успех 50%: +200–500 очков и столько же крышек; поражение: -30–50 HP |
| `2` | Лагерь | Перевязка: 10 крышек за до 10 HP; стимулятор: 25 крышек за до 30 HP |
| `3` | Казино Нью-Вегаса | Ставка 20% крышек с округлением вниз; минимум 5 крышек для участия |
| `0` | Завершение | Выход с фиксацией текущего счета |

В казино исходы 0–49 дают выплату двух ставок и 100 очков;
исход 0 дает 500 очков вместо 100. Исходы 50–99 означают потерю ставки;
при 99 дополнительно наносится 30 HP урона.

После выполненного действия живой герой получает еще 10 очков выживания.
Неверная команда, отмена, нехватка денег и отказ действия не дают очков
и не увеличивают номер хода. Смертельный ход не дает бонуса выживания.
Здоровье ограничено диапазоном 0–100, накопление очков и крышек защищено
от знакового переполнения. Рейд доступен без крышек.

Описание относится к объединенной версии трех механик. Пока игровые PR
не слиты, в `main` могут оставаться заглушки.

## 7. Сборка и результаты проверок

Сборка финальной версии после слияния трех игровых PR:

```bash
git switch main
git pull --ff-only
g++ game.cpp -o game
./game
```

Сохранили совместимость с прежним именем: `g++ main.cpp -o main`.
`main.cpp` включает `game.cpp`, поэтому эти файлы компилируем
по отдельности, а не одной командой вместе.

Строгая сборка и базовые проверки:

```bash
make test
```

Проверки всех механик после их объединения:

```bash
make test
for module in risk heal gamble; do
  g++ -std=c++17 -Wall -Wextra -Wpedantic -Werror \
    -fsanitize=undefined -fno-sanitize-recover=all \
    "tests/${module}_tests.cpp" -o "build/${module}-tests" || exit 1
  "./build/${module}-tests" || exit 1
done
```

В отдельной feature-ветке присутствует только тест ее механики.
Сборка и проверки каждой опубликованной игровой ветки прошли GitHub Actions.
Мы также локально объединили три ветки без конфликтов и получили:

```text
All game checks passed.
Risk checks passed (1000 seeds).
Healing checks passed (15 scenarios).
Gamble checks passed (1000 seeds and boundary cases).
```

Проверены смерть, отсутствие бонуса за невыполненный ход, нехватка денег,
предел здоровья, отмена покупки, неверный ввод, EOF, джекпот, проклятие
и граничные значения int.

Пробная партия с рейдом, лечением и рулеткой завершилась со счетом
**130 очков**. Это техническая проверка, не совместный турнир.

**Совместная партия:** ожидается. **Итоговый командный рекорд:** не зафиксирован.

## 9. Контрольные вопросы

**1. Чем GitHub Flow отличается от прямого push в main?**
Мы разрабатываем в отдельной ветке и проводим проверку через PR
до попадания изменения в основную ветку. Прямой push исключает этот
обязательный этап обсуждения и ревью.

**2. Почему Request changes блокирует слияние и как обновляется PR?**
При применимых правилах обязательного ревью запрос исправлений
препятствует слиянию до его разрешения. Новые коммиты отправляются
в ту же head-ветку, поэтому существующий PR обновляется автоматически.
После исправления рецензент повторяет проверку и ставит Approve.

**3. Что произойдет с Issue #4 при Closes #4 в описании PR?**
После слияния PR в default-ветку GitHub автоматически закроет
связанную задачу #4. Само открытие PR ее не закрывает.

**4. В чем польза Squash and merge?**
Рабочие коммиты одного PR объединяются в один итоговый коммит.
В `main` остается компактная история завершенных задач,
а не последовательность черновых правок.

**5. Зачем включать Dismiss stale pull request approvals?**
Одобрение относится к уже проверенной версии. После новых коммитов
устаревшее одобрение сбрасывается, чтобы непроверенный код
не попал в `main` под старым Approve.
